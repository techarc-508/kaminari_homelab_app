## 2. Room schema changes

### Version

| Property | Before | After |
|---|---|---|
| `KaminariDatabase` version | 1 | 2 |
| `exportSchema` | false | true |
| Schema files | `1.json` (generated before edits) | `1.json`, `2.json` |
| Destructive fallback | none | none |

### Existing tables — unchanged

`server_profiles`, `topic_subscriptions`, `messages` keep the same columns,
primary keys, indices and foreign keys. Message deduplication on
`(profileId, messageId)`, saved flags, read flags and sample flags are untouched.

### New table: `outbox_entries`

Primary key `clientId` (client-generated UUID string). Columns:
`profileId`, `topic`, `title`, `body`, `priority`, `tagsJson`, `clickUrl`,
`attachmentUrl`, `actionsJson`, `delay`, `state`, `attemptCount`, `retryable`,
`lastError`, `serverMessageId`, `createdAt`, `updatedAt`, `acceptedAt`.

- Foreign key `profileId → server_profiles(id)` with `ON DELETE CASCADE`.
- Indices: `(profileId, createdAt)`, `(profileId, state)`.
- `state` is persisted by name; `OutboxState.fromPersisted` treats unknown
  values as `QUEUED` (safe default).
- `attachmentUrl` stores URL/metadata only. Binary upload is not represented.

### New table: `activity_events`

Primary key `id` (string). Columns: `profileId`, `type`, `severity`, `summary`,
`correlationId`, `messageId`, `topic`, `createdAt`.

- Foreign key `profileId → server_profiles(id)` with `ON DELETE CASCADE`.
- Indices: `(profileId, createdAt)`, `(correlationId)`.
- The schema has no body column: activity summaries must not contain message
  bodies or secrets.

### New table: `command_requests`

Primary key `commandId`. Columns: `profileId`, `actionId`, `target`, `argsJson`,
`nonce`, `issuedAt`, `expiresAt`, `requiresConfirmation`, `confirmedAt`,
`status`, `resultJson`, `resultSummary`, `createdAt`, `updatedAt`.

- Foreign key `profileId → server_profiles(id)` with `ON DELETE CASCADE`.
- Indices: `(profileId, createdAt)`, **unique** `nonce` (replay protection).
- `status` persisted by name; Stage E owns the transition policy.

### Migration

`KaminariDatabase.MIGRATION_1_2` executes only `CREATE TABLE IF NOT EXISTS` and
`CREATE INDEX IF NOT EXISTS` statements for the three new tables. It does not
drop, rename, rewrite or backfill any existing table or row.

`KaminariDatabase.build()` registers `MIGRATIONS = arrayOf(MIGRATION_1_2)` and
does **not** call `fallbackToDestructiveMigration()`.

## 4. DAO and state-transition behavior

### `OutboxDao`

| Method | Behavior | Test |
|---|---|---|
| `insert` | Persists a new entry. Duplicate `clientId` fails at the primary key. | `OutboxDaoTest` |
| `claim(clientId, now)` | `QUEUED → SENDING`, increments `attemptCount`; returns 0 for a second claim. | `claim is single winner...` |
| `complete(...)` | Only transitions from `SENDING` to a terminal state; late calls return 0. | same |
| `requeue` | Only `FAILED`/`AMBIGUOUS → QUEUED`; accepted rows cannot be requeued. | `requeue is limited...` |
| `recoverStuckSending` | Process restart: old `SENDING` rows become `AMBIGUOUS`, not auto-resent. | `stuck sending recovery...` |
| `deleteIfUnsent` | Deletes `QUEUED`/`FAILED`/`AMBIGUOUS` only; accepted rows are retained. | `cancel refuses accepted...` |
| `prune` | Removes terminal rows older than the cutoff and rows beyond the keep cap; never removes `QUEUED`/`SENDING`. | `prune removes old terminal...` |

All transitions are conditional SQL updates (`WHERE state = ...`), so two
senders cannot both claim the same row. `SENDING` is never treated as success.

### `ActivityDao`

- `observeRecent(profileId, limit)` is profile-scoped and newest-first.
- `prune(profileId, cutoff, keepMax)` enforces the approved 90 days / 5,000
  rows per profile policy; other profiles are untouched.
- Rows cascade when the profile is deleted.

### `CommandDao`

- `nonce` is unique at the database level.
- `markStatus` is conditional on the expected status; a stale executor cannot
  overwrite a terminal result.
- `expireOverdue` only expires `SUBMITTED` rows past `expiresAt` for the profile.
- `prune` removes terminal rows only; `SUBMITTED` rows are never pruned.
- Queries are profile-scoped.

### `MessageDao` and topic queries

- `search(profileId, query, limit, offset)` performs bounded substring search on
  title/body/topic. It is not FTS; see risk R-25.
- `observeSaved(profileId, limit)` backs the Saved Inbox filter.
- `observeUnreadCounts(profileId)` returns per-topic unread counts.
- `TopicSubscriptionDao.count(profileId)` supports profile-scoped counts.

No repository class was added in Stage A. Repositories, receive-event
transactions and publish orchestration are Stage C by design (T4A-06).

## 7. Security and data-integrity review

- No destructive migration, no `fallbackToDestructiveMigration`, no `DROP`.
- Profile isolation is enforced in every new DAO query; foreign keys cascade on
  profile deletion, matching existing behavior.
- Outbox claim/complete are conditional and cannot double-send through the DAO.
- `SENDING` rows recovered after a process restart become `AMBIGUOUS`, not
  automatically resent. This prevents duplicate publishes without idempotency.
- Command `nonce` is unique; status transitions are conditional.
- Activity rows store summaries only, not message bodies or credentials.
- No secrets, tokens, URLs or server credentials are stored in the new tables.
- No network, shell, PVE or command execution code was added in Stage A.

## 8. Performance and resource implications

- New tables are empty until Stages B–E use them; no startup cost beyond Room
  schema validation.
- All list queries are bounded by `LIMIT`; prune methods keep storage bounded.
- Indexes cover the profile/time and profile/state access paths used by the
  planned UI.
- `LIKE` search can scan within a profile; bounded by `LIMIT`/`OFFSET`, but not
  FTS. Measure on a low-end device (R-25).
- APK growth is ~91 KB; no new runtime dependency.
